# Publishing Plan: crates.io + PyPI + CRAN

Plan for releasing the three artifacts of this repository:

| Registry  | Artifact       | Name           | Source dir       | Status |
|-----------|----------------|----------------|------------------|--------|
| crates.io | Rust core      | `koopman-dmd`  | `koopman-dmd/`   | Name available |
| PyPI      | Python binding | `koopman-dmd`  | `koopman-dmd-py/`| Name available |
| CRAN      | R package      | `koopman.dmd`  | `koopman-dmd-r/` | Name available |

All three names were verified free on 2026-08-05 (crates.io API 404, PyPI JSON API 404,
CRAN package index 404). Claim them early — crates.io and PyPI are first-come.

**Recommended order: crates.io → PyPI → CRAN.** This is not arbitrary. Publishing the core
crate first lets the R binding switch its `koopman-dmd` dependency from a `path = "../../../koopman-dmd"`
to a registry version, which is what makes `cargo vendor` able to produce a self-contained
CRAN tarball (see Phase 3).

## Findings from the current tree

Verified against the working copy, not assumed:

**Rust core** is in good shape. `cargo package --list` produces a clean file set; crate
metadata has `description`, `license`, `repository`, `keywords`, `categories`. Gaps are
cosmetic-but-blocking (no `README`/`LICENSE` inside the crate directory, so the published
`.crate` ships without a license file).

**Python binding** builds and tests in CI today via `maturin develop`, but `pyproject.toml`
carries no author, README, URLs, or classifiers, and there is no wheel-building workflow —
only a source build. Nothing currently produces distributable artifacts.

**R package** is the long pole. Three hard blockers:

1. `man/` is **empty** — zero `.Rd` files. `R CMD check` fails immediately; CRAN will not
   look at a package with undocumented exports. The roxygen source is largely there
   (83 `@param`, 24 `@return`, 28 `@export` across `R/*.R`), so this is mostly a matter of
   running `roxygen2` — but **0 `@examples`** exist, and CRAN expects runnable examples on
   exported functions. That is genuine new writing.
2. `NAMESPACE` is hand-maintained despite its "Generated by roxygen2" header, and exports
   S3 methods directly (`export(predict.dmd)` alongside `S3method(predict, dmd)`), which
   draws a check NOTE.
3. The Rust crate at `koopman-dmd-r/src/rust` depends on the core via a relative path that
   climbs out of the package directory. A CRAN tarball contains only the package directory,
   so **the submitted package cannot build as it stands**.

### The CRAN size question — measured, not guessed

CRAN's policy is that a source tarball should stay near 5 MB. Vendoring is mandatory
(CRAN build machines are offline), so I vendored the dependency tree and measured:

| Vendor strategy | Compressed (`tar.xz`) |
|---|---|
| Naive `cargo vendor` from the current workspace | **14 MB** |
| Standalone crate, `faer` default features off | 11 MB |
| \+ drop `loom`/`tracing*`, strip tests/benches/examples/docs | 7.8 MB |
| \+ drop `windows-sys-0.61`, prune `windows-sys-0.42` to used modules | **4.1 MB** |

The bloat has a single root cause worth recording. `faer`'s `std` feature enables
`private-gemm-x86` on x86_64, which pulls `spindle` → `loom` → `tracing-subscriber` →
`nu-ansi-term`. `loom` is a `cfg(loom)`-only dependency that **can never compile in a normal
build**, yet it drags in 4.2 MB of compressed `windows-sys` bindings. Removing that dead
chain, plus pruning `windows-sys-0.42` down to the `Win32::System::Threading` and
`Win32::Foundation` modules that `atomic-wait` actually imports, is what gets us from 14 MB
to 4.1 MB.

Two things I checked so we don't waste effort:
- **Upgrading `faer` 0.22 → 0.24 does not help.** I resolved a 0.24 lockfile; the same
  `spindle`/`loom`/`windows-sys` chain is still present. Do not treat the upgrade as a size fix.
- **Feature trimming alone does not get us under.** It only bought 14 MB → 11 MB. The
  pruning step is the one that matters.

For calibration, real Rust-backed CRAN packages today: `b64` 1.0 MB, `orbweaver` 1.1 MB,
`arcgisutils` 2.6 MB, `hellorust` 4.5 MB, `prqlr` **9.0 MB**. At 4.1 MB we are comfortably
inside precedent, and `prqlr` shows there is headroom if a prune step later proves fragile.

## Phase 0 — Repository hygiene (prerequisite for all three)

- `koopman_dmd_demo.pdf` and `.DS_Store` are untracked in the working copy. Add `.DS_Store`
  to `.gitignore`; decide whether the PDF is a release asset or belongs in `docs/`.
- Add a `CHANGELOG.md` (Keep a Changelog format). CRAN wants `NEWS.md` for the R package —
  keep them separate, since they version independently after 0.1.0.
- Decide the versioning policy. Recommendation: **release all three at 0.1.0 together**,
  then let them drift — the Rust crate will need patch releases the R package should not
  be forced to follow, and CRAN actively discourages frequent resubmission (a package
  updated more than roughly every 1–2 months gets pushback).
- Add `rust-version` (MSRV) to the core `Cargo.toml` and verify it in CI. CRAN in particular
  will build against whatever Rust its machines carry; knowing the floor matters.

## Phase 1 — crates.io (`koopman-dmd`)

Lowest-friction of the three; realistically a day's work.

1. **Complete crate metadata** in `koopman-dmd/Cargo.toml`: add `authors`, `readme`,
   `documentation = "https://docs.rs/koopman-dmd"`, `homepage`, `rust-version`.
2. **Put `LICENSE` and a `README.md` inside `koopman-dmd/`.** The dry-run file list confirms
   the published `.crate` currently contains neither — only files under the crate directory
   ship. Symlinks are not followed by `cargo package`; copy them.
3. **Mark the binding crates unpublishable**: `publish = false` in both `koopman-dmd-py/Cargo.toml`
   and `koopman-dmd-r/src/rust/Cargo.toml`. Without this, a workspace-wide `cargo publish`
   will try to push them, and the py/r crates have path dependencies that cannot be published.
4. **Trim the shipped file set.** `tests/cross_validation.py` is currently included in the
   `.crate`; add an `exclude` list or move it. Consider excluding `benches/` too.
5. **Verify docs.rs will build.** Run `cargo doc --no-deps` clean of warnings; the crate-level
   doc example in `lib.rs` is a doctest and must pass — `cargo test --doc`.
6. **Publish**: `cargo publish -p koopman-dmd --dry-run`, inspect, then publish for real.

Note the one-way door: **crates.io versions are immutable and cannot be deleted**, only
yanked. Do the dry run.

## Phase 2 — PyPI (`koopman-dmd`)

The build already works; what is missing is metadata and a release pipeline.

1. **Fill out `pyproject.toml`**: `authors`, `readme`, `[project.urls]`, `classifiers`,
   `keywords`. Add a `README.md` and `LICENSE` inside `koopman-dmd-py/`.
2. **Raise the Python floor and enable `abi3`.** `requires-python = ">=3.8"` targets an
   end-of-life Python. Move to `>=3.9` and build with pyo3's `abi3-py39` feature — this
   produces **one wheel per platform** instead of one per Python version per platform,
   cutting the build matrix by roughly 4–5×.
3. **Add a release workflow** using `PyO3/maturin-action`, building:
   - Linux `manylinux` x86_64 + aarch64
   - macOS x86_64 + arm64
   - Windows x86_64
   - an sdist (required so non-covered platforms can build from source)
4. **Use Trusted Publishing (OIDC)** rather than a long-lived API token — configure the
   publisher on PyPI against this repo and the release workflow.
5. **Test the artifacts before publishing.** Push to **TestPyPI** first, then `pip install`
   the wheel into a clean venv on at least one platform and run `koopman-dmd-py/tests/`
   against the *installed* package, not the development build.
6. **Confirm the import name.** The distribution is `koopman-dmd`; the module is
   `koopman_dmd`. Make sure the README documents that.

## Phase 3 — CRAN (`koopman.dmd`)

The most work and the only submission with a human reviewer. Budget 2–4 weeks including
review turnaround.

### 3a. Make the package self-contained

> **No build-time downloads — including from crates.io.** CRAN's *Using Rust in CRAN
> packages* document allows only two options: bundle the sources, or download a fixed
> version from "a secure and reliable site" with a checksum embedded in the source package.
> crates.io does not qualify on CRAN's own terms — the document states that CRAN "does not
> regard github.com (which used to host the index of crates.io and still hosts most of the
> crates it indexes) as sufficiently reliable," and that downloading "should be avoided if
> at all possible," since CRAN keeps packages installable for many years. The prescribed
> route is `cargo vendor` + an xz-compressed bundle, which is what this plan does. The only
> sanctioned remote option is a site **under the maintainer's control**, needed only if the
> bundle is too large to include — at 4.1 MB it is not.

- **Switch the Rust dependency to the registry.** Once Phase 1 lands, change
  `koopman-dmd = { path = "../../../koopman-dmd" }` to `koopman-dmd = "0.1"`. This is the
  step that makes vendoring possible — the path dependency escapes the package directory
  and cannot survive tarballing. Note this registry reference is resolved **once, on the
  maintainer's machine, when generating `vendor.tar.xz`**; the submitted package builds
  `--offline` against the vendored sources and never reaches the network.
- **Remove `koopman-dmd-r/src/rust` from the root workspace `members`.** It needs its own
  `Cargo.lock` so that workspace dev-dependencies (`criterion`, which drags in
  `plotters` → `web-sys`) stay out of the vendored tree.
- **Vendor with pruning.** Script it (`tools/vendor-for-cran.sh`) so it is reproducible:
  `cargo vendor`, delete the dead `loom`/`tracing*` chain and unneeded `windows-sys`
  modules, strip `tests/`/`benches/`/`examples/`/docs from vendored crates, rewrite the
  `files` map in each `.cargo-checksum.json`, then `tar cJf src/rust/vendor.tar.xz`.
  Target confirmed achievable: **4.1 MB**.
- **Commit the untracked build artifacts problem.** `src/entrypoint.o` and
  `src/koopman.dmd.so` exist in the working tree; they must never enter the tarball.

### 3b. Satisfy CRAN's Rust policy

Requirements below are taken from the *Using Rust in CRAN packages* document
(<https://cran.r-project.org/web/packages/using_rust.html>) and the main Repository Policy.
Each is a rejection trigger:

- **Write a `configure` and `configure.win` script.** Required, and currently absent. It
  must check that `cargo` and `rustc` are present *and* of adequate version, searching both
  the system path **and `~/.cargo/bin`** (personal installs are frequently not on the path).
  If missing, it must tell the user to install them via their distro (`apt-get install cargo rustc`,
  `dnf install cargo`) or rustup — and **must not attempt to install them itself**.
- **Report the `rustc` version into the installation log before compiling**, the way R does
  for C/C++/Fortran compilers, so failures are diagnosable.
- **Keep version requirements conservative and test against an old toolchain.** CRAN's Linux
  check machines use distro-packaged Rust, which lags badly. The policy asks for testing with
  a cargo at least two years old, preferably four or more.

  > **This is now a confirmed conflict, not a hypothetical.** Phase 1 measured the crate's
  > true MSRV as **Rust 1.85** (released Feb 2025) — set not by our code but by
  > `generativity 1.2.1`, an edition-2024 transitive dependency of `faer`. Rust 1.85 is
  > roughly *18 months old*, well short of the two-to-four years CRAN asks for, and newer
  > than what Debian stable and older Ubuntu LTS ship. Options, to be decided before 3c
  > work begins:
  > 1. **Pin older deps in the vendored tree.** `generativity 1.1.0` is edition 2021 and
  >    works on 1.84; the vendor lockfile can pin it. Gains one Rust version — probably
  >    not enough on its own, but stacks with option 2.
  > 2. **Pin an older `faer`** for the CRAN build than the crates.io crate depends on,
  >    accepting that the R package lags the Rust core. Needs an MSRV bisection across
  >    faer versions to find one that clears a realistically old toolchain.
  > 3. **Declare the requirement** in `SystemRequirements` (e.g. `rustc (>= 1.85)`) and
  >    let `configure` fail with a clear message. Permitted — the policy says to "state
  >    carefully any version requirement" — but raises the odds of a reviewer objection
  >    and of failures on CRAN's own older check machines.
  >
  > Do the faer MSRV bisection **before** investing in the documentation work in 3c; if no
  > acceptable combination exists, that changes whether CRAN is viable at all.
- The build must be **fully offline** — `cargo build --offline` against the vendored
  sources, with a `.cargo/config.toml` generated at build time pointing at `vendor/`.
- `CARGO_HOME` must be set **inside the build directory** and cleaned up. Cargo must not
  write to the user's home directory.
- Respect the **core limit**: `cargo build` defaults `-j` to the logical CPU count, which
  exceeds what CRAN permits. Set it explicitly to `-j 2` (policy allows 1 or 2).
- Authorship and copyright for the Rust code — **including every vendored dependency** —
  must be recorded in `DESCRIPTION`. Add `inst/AUTHORS` and a
  `person("The authors of the dependency Rust crates", role = "ctb", comment = "see inst/AUTHORS file for details")`
  entry in `Authors@R`.
- Bundle the vendored sources with **xz** compression specifically (`vendor.tar.xz`).
- Review `Makevars`. `PKG_LIBS` currently hardcodes `-lresolv`, which is a macOS-ism;
  confirm it is correct or made conditional for Linux builds.
- `SystemRequirements: Cargo (Rust's package manager), rustc` is already present — good.

`string2path` (v0.1.5) is cited by CRAN itself as the reference implementation of this
setup; worth reading its `configure`, `Makevars`, and vendoring script before writing ours.

### 3c. Documentation (the real work)

- **Generate `man/`**: install `rextendr`, run `rextendr::document()` / `roxygen2::roxygenise()`.
  This produces the `.Rd` files and regenerates `NAMESPACE` correctly, which also fixes
  the `export(predict.dmd)` + `S3method` duplication.
- **Write `@examples` for every exported function.** This is the largest single task —
  currently zero exist across 24+ exports. Examples must run in under ~5s each and must not
  write outside `tempdir()`. Plotting functions (`mesochronic_compute`, `classify_phase_space`)
  will need small grids to stay inside the time budget.
- **Write a vignette.** Not strictly required, but for a method-heavy statistical package it
  substantially improves review odds. `demo.R` and `generate_plots.R` are strong raw material.
- **Add `NEWS.md`, `.Rbuildignore`** (currently missing — must exclude `src/rust/target`,
  `.github`, dev scripts), and a `cran-comments.md`.
- **Package-level `?koopman.dmd` help page** and a `README.md` for the package directory.
- Cite the underlying methods (Schmid, Mezić, Arbabi & Mezić) in `Description` using the
  required `<doi:...>` format — CRAN checks this.

### 3d. Check and submit

- `R CMD build` then `R CMD check --as-cran` locally until **0 errors, 0 warnings, 0 notes**.
  A first submission with notes usually bounces.
- Run **`rhub::rhub_check()`** across Windows, macOS (x86_64 + arm64), and Linux
  (r-devel with both gcc and clang), plus **win-builder** r-devel and r-release. Rust
  packages fail on platform differences far more often than pure-R ones, so this step is
  not optional.
- Submit via <https://cran.r-project.org/submit.html> with `cran-comments.md` explaining
  the vendored Rust sources and the tarball size.
- Expect at least one round of reviewer comments. Common asks for Rust packages: justify
  the bundled sources, confirm no network access at build time, confirm the license of
  every vendored crate is compatible.

## Cross-cutting: CI and release automation

Extend `.github/workflows/`:

- `release-crate.yml` — tag-triggered `cargo publish`, gated on the full test suite.
- `release-python.yml` — `maturin-action` matrix → wheels + sdist → PyPI via Trusted Publishing.
- `check-r-cran.yml` — build the vendored tarball and run `R CMD check --as-cran` on
  Linux/macOS/Windows on every PR. This is what keeps the CRAN package from rotting between
  submissions.
- Add a `vendor-size` guard that fails CI if the pruned tarball exceeds ~4.5 MB, so a
  dependency bump cannot silently push us over the CRAN limit.

## Risks

| Risk | Severity | Mitigation |
|---|---|---|
| CRAN rejects on tarball size | Medium | Measured at 4.1 MB pruned; `prqlr` ships 9.0 MB today |
| Vendor-prune script breaks on a `faer`/`extendr` bump | Medium | CI size + build guard; prune list is data-driven, not hardcoded paths |
| Distro cargo/rustc on CRAN's Linux farm too old for `faer` | **High — confirmed** | MSRV measured at Rust 1.85 (Feb 2025) via `generativity`/edition-2024 under `faer`. Shorter than CRAN's requested 2–4 year window. Bisect faer versions for a lower floor before starting 3c |
| CRAN reviewer objects to bundled Rust sources | Low | Precedent is well established; `inst/AUTHORS` + `cran-comments.md` address it |
| Writing 24+ runnable examples takes longer than expected | Medium | Largest single task; start it in parallel with Phase 1 |
| Name squatted between now and publication | Low | Claim crates.io + PyPI names early (Phases 1–2 are fast) |

## Suggested sequencing

```
Week 1   Phase 0 hygiene, Phase 1 crates.io publish
         (start R examples/vignette writing in parallel — it is the critical path)
Week 2   Phase 2 PyPI: metadata, abi3, wheel matrix, TestPyPI, publish
Week 3-4 Phase 3 CRAN: vendoring script, docs generation, examples, rhub matrix
Week 5   CRAN submission; expect 1-2 review rounds over the following 2-4 weeks
```
